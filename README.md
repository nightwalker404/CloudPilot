# CloudPilot

A conversational AI agent that provisions real infrastructure from natural language. Tell it what you want — for example:

> "a VPS with 5GB RAM, 20GB storage, 2 cores, name it rtx234, Ubuntu"

CloudPilot uses an LLM to understand the request, decide which tools to call, and execute real infrastructure operations — currently starting with VM provisioning through the [Incus](https://linuxcontainers.org/incus/) REST API.

It can also search the web through a self-hosted [SearXNG](https://docs.searxng.org/) instance when the model needs information outside its own knowledge.

## Architecture

```text
┌──────────────┐
│   Frontend   │
│ index.html   │
└──────┬───────┘
       │ HTTP
       ▼
┌──────────────────────┐
│       FastAPI        │
│       Backend        │
│                      │
│  Chat + Dispatcher   │
│  Tool Registry       │
└──────┬───────────────┘
       │
       ├───────────────────────┐
       │                       │
       ▼                       ▼
┌────────────────┐      ┌──────────────────┐
│    Ollama      │      │    MongoDB       │
│      LLM       │      │ Conversation     │
│                │      │    History       │
└────────────────┘      └──────────────────┘
       │
       │ tool calls
       ▼
┌───────────────────────────────────────────┐
│                 Tools                     │
│                                           │
│  create_vm ──────▶ Incus API (mTLS)       │
│                                           │
│  web_search ─────▶ SearXNG ─────▶ Web    │
└───────────────────────────────────────────┘
```

### Components

* **Backend** — FastAPI application responsible for chat requests, conversation persistence, tool dispatching, and communication with Ollama.
* **Ollama** — Hosts the local LLM used for chat and tool calling.
* **Tool calling** — The model decides when a tool is needed. The dispatcher executes the requested tool and feeds the result back to the model. `app/tools/registry.py` provides the central registry for the available tool sets.
* **Hosting tool (`create_vm`)** — Builds an Incus VM payload containing CPU, memory, disk, OS, and name; calls the Incus REST API over mTLS; waits for the creation operation; starts the VM; polls for its IP; and returns a human-readable result with credentials generated by cloud-init.
* **Web search tool (`web_search`)** — Searches the web through a self-hosted SearXNG instance. No external search API key is required.
* **MongoDB** — Stores conversations and message history so a `conversation_id` can be resumed across requests.
* **Frontend** — A static `frontend/index.html` used for testing and demonstration. It requires no frontend build step.

## Requirements

* Docker + Docker Compose
* An Incus server reachable from the backend
* Incus mTLS client certificate, client key, and server certificate
* A GPU-capable host is recommended for reasonable Ollama latency
* An Ollama model with reliable tool-calling support
* Internet access for SearXNG to retrieve web results

The Docker Compose stack includes:

* Ollama
* MongoDB
* SearXNG
* CloudPilot backend
* CloudPilot frontend

## Setup

### 1. Configure Incus certificates

Place the Incus certificates in:

```text
certs/
├── client.crt
├── client.key
└── server.crt
```

The backend uses these certificates when communicating with the Incus API over mTLS.

### 2. Configure environment variables

CloudPilot uses a `.env` file as the source of application configuration.

For Docker Compose, service-to-service connections should use Docker service names rather than `localhost`.

Example:

```env
### AI Model ###
LLM_BASE_URL=http://ollama:11434
MODEL=qwen2.5-coder:7b

### App Configuration ###
APP_NAME=CloudPilot
DEBUG_MODE=True
APP_PORT=8000
APP_HOST=0.0.0.0

### MongoDB Configuration ###
MONGO_URI=mongodb://admin:password@mongodb:27017
MONGO_INITDB_ROOT_USERNAME=admin
MONGO_INITDB_ROOT_PASSWORD=password
MONGO_DB_NAME=cloudpilot

### Incus Configuration ###
INCUS_URL=https://host.docker.internal:8443

### WebSearch Config ###
SEARXNG_URL=http://searxng:8080
```

> **Docker networking:** `localhost` inside the backend container refers to the backend container itself. Use `ollama`, `mongodb`, and `searxng` when connecting to those Compose services.

### 3. Pull an Ollama model

The model should support tool calling reliably. For example:

```bash
docker exec -it ollama ollama pull qwen2.5-coder:7b
```

Larger instruction-tuned models can also be used if available on your hardware.

### 4. Start the stack

```bash
docker compose up -d --build
```

Check the running containers:

```bash
docker compose ps
```

The expected services are:

```text
ollama
mongodb
cloudpilot-searxng
cloudpilot-backend
cloudpilot-frontend2
```

### 5. Check the backend

```bash
curl http://localhost:8000/health
```

### 6. Test web search

SearXNG is exposed locally on port `8080`:

```bash
curl "http://localhost:8080/search?q=Docker+containers&format=json"
```

You can also verify that the backend container can reach SearXNG:

```bash
docker exec cloudpilot-backend \
  python -c "import requests; r=requests.get('http://searxng:8080/search', params={'q':'Docker containers','format':'json'}, timeout=15); print(r.status_code)"
```

A successful response should return:

```text
200
```

### 7. Test the chat endpoint

```bash
curl -X POST http://localhost:8000/chat \
  -H "Content-Type: application/json" \
  -H "X-User-ID: demo-user" \
  -d '{
    "messages": [
      {
        "role": "user",
        "content": "Search for the latest news about Docker containers"
      }
    ]
  }'
```

### 8. Open the frontend

The frontend is included in the Docker Compose stack and is available at:

```text
http://localhost:3000
```

Alternatively, for frontend development/testing, you can serve the static files directly:

```bash
cd frontend
python3 -m http.server 5500
```

Then open:

```text
http://localhost:5500/index.html
```

Set the backend Base URL to:

```text
http://localhost:8000
```

and provide any `X-User-ID` value.

## API Routes

| Method   | Path                  | Description                                              |
| -------- | --------------------- | -------------------------------------------------------- |
| `GET`    | `/health`             | Liveness/health check                                    |
| `POST`   | `/chat`               | Send a chat request and optionally resume a conversation |
| `POST`   | `/conversations`      | Create an empty conversation                             |
| `GET`    | `/conversations`      | List conversations for the current user                  |
| `GET`    | `/conversations/{id}` | Get full conversation history                            |
| `DELETE` | `/conversations/{id}` | Delete a conversation                                    |

### `/chat`

Request body:

```json
{
  "messages": [
    {
      "role": "user",
      "content": "Create a VM with 2 cores, 5GB RAM and 20GB disk"
    }
  ],
  "conversation_id": "optional-id",
  "model": "optional-model",
  "stream": false,
  "temperature": 0.7,
  "max_tokens": 2000
}
```

The endpoint requires:

```text
X-User-ID
```

header.

Example:

```bash
curl -X POST http://localhost:8000/chat \
  -H "Content-Type: application/json" \
  -H "X-User-ID: demo-user" \
  -d '{
    "messages": [
      {
        "role": "user",
        "content": "Create a VM with 2 cores, 5GB RAM and 20GB disk named rtx234 using Ubuntu"
      }
    ]
  }'
```

All routes except `/health` require an `X-User-ID` header.

> **Security:** `X-User-ID` is currently only an identifier, not an authentication mechanism. Anyone who can reach the API can potentially impersonate another user by changing the header. Do not expose the API publicly without adding proper authentication and authorization.

## Available Tools

| Tool                                          | Description                                                                                  |
| --------------------------------------------- | -------------------------------------------------------------------------------------------- |
| `create_vm(cpu, memory, disk, vm_name?, os?)` | Creates and starts a VM through the Incus REST API and returns its name, credentials, and IP |
| `web_search(query, max_results?)`             | Searches the web through the local SearXNG instance and returns the top results              |

### `create_vm`

The hosting tool:

1. Validates the requested VM parameters.
2. Builds the Incus VM configuration.
3. Sends the request to the Incus REST API using mTLS.
4. Waits for the Incus operation to complete.
5. Starts the VM.
6. Polls for the VM's IP address.
7. Returns a human-readable result.

Cloud-init is used to configure the VM and provide login credentials.

### `web_search`

The web search tool:

1. Receives a search query from the LLM.
2. Sends the query to the local SearXNG service.
3. Requests JSON results.
4. Extracts the top results.
5. Returns titles, URLs, and snippets to the LLM.

SearXNG runs as part of the Docker Compose stack, so CloudPilot does not require a Tavily API key.

## Docker Networking

CloudPilot uses a dedicated Docker network:

```text
cloudpilot-net
```

Services communicate using their Compose service names.

For example:

```text
Backend
   │
   ├── http://ollama:11434
   ├── mongodb:27017
   └── http://searxng:8080
```

From the host machine, the published ports are:

```text
Frontend  → localhost:3000
Backend   → localhost:8000
SearXNG   → localhost:8080
MongoDB   → localhost:27017
Ollama    → localhost:12434
```

Note that Ollama's host port is `12434`, while its internal Docker port remains `11434`.

## Known Issues

### Tool-calling reliability depends on the model

Tool calling is highly dependent on the selected LLM.

Small or code-focused models may sometimes respond with plain text instead of emitting a structured tool call, especially when a request contains multiple parameters.

For example:

```text
Create a VPS with 5GB RAM, 20GB disk, 2 cores,
name it rtx234 and use Ubuntu.
```

If the model does not reliably call tools, use a larger instruction-tuned model with strong tool-calling support.

### No input bounds on `create_vm`

CPU, memory, and disk parameters are type-checked but should also have sensible range validation before production deployment.

A malformed or unreasonable request can otherwise be forwarded to Incus.

### CORS is wide open

The backend currently allows all origins for local development:

```python
allow_origins=["*"]
```

Restrict this before deploying the API outside a trusted development environment.

### No real authentication yet

The current API relies on:

```text
X-User-ID
```

for user identification.

This is not authentication. A production deployment needs proper authentication and authorization before users can provision infrastructure.

### Docker service readiness

`depends_on` controls container startup order but does not necessarily mean a dependency is fully ready to accept connections.

If MongoDB, Ollama, or another dependency starts slowly, the backend may need to be restarted or enhanced with connection retry/health-check logic.

### Web search quality depends on SearXNG engines

SearXNG aggregates results from configured search engines. Result availability and quality can vary depending on the engines enabled and their availability.

## Roadmap

CloudPilot is the first piece of a larger multi-channel infrastructure hosting agent.

Planned capabilities include:

* Website chat
* Telegram integration
* WhatsApp integration
* User balance and account management
* Infrastructure provisioning
* Payment links
* Automated credential delivery
* Ansible integration
* Packer golden images
* Kubernetes provisioning and management
* Additional infrastructure providers

The long-term goal is an end-to-end hosting agent that can understand a user's infrastructure request, provision the required resources, handle billing, and deliver access details through the user's preferred communication channel.
